# 现有投资研究机制核对与三层目录设计修正

核对日期：2026-10-10。依据：`Skill Backup` 中 21 个 SKILL.md 的流程和接口、相关本地脚本、TCOM 档案，以及 LLY 的一份预测偏差分诊记录。核心编排与反馈文件已逐段核对；其他专项 skill 主要核对定位、输入输出与交接规则。本报告没有重新验证公司披露中的投资事实，也没有执行分析、刷新、交易或定时任务。

## 1. 先纠正此前的判断

现有系统已经有研究依赖链、事件分诊、预测偏差反馈、版本审核、持仓纪律检查和模拟组合记录。问题不能再表述为“建立一套此前没有的反馈机制”。更准确的任务是：让已经存在的反馈流程在资料组织上连得起来，明确接口，并使每一次判断变化都能被复查。

此前 10 月 9 日的方案在没有读取这些 skills 的情况下，过早提出了结构性重建建议。它只能作为候选方法清单，不能作为现状诊断或迁移规格。其中“缺少反馈机制”“需要从零引入可证伪判断”的概括应撤回。现有 06 的分歧驱动表、战略交接中的证伪条件，以及偏差分诊已经承担了这些职责。

文件保存位置也确实不妥：`research-summary` 明确把 `Projects/基本面分析汇总/` 用作公司研究总结 HTML 的输出位置。系统设计应单独放在本目录。此前文件已由用户统一移至本目录，作为历史草稿保留；入口和主报告保留更正提示。

## 2. 现有系统怎样运转

### 2.1 建档不是七篇互不相干的报告

| 环节 | 核心作用 | 下游关系 |
|---|---|---|
| 入库 | 登记公司、建目录、取得原始披露和财务底稿 | 只准备材料，不生成研究结论 |
| 01 企业文化 | 当前编排调用使命愿景、领导力、治理三个子 skill 后合并 | 为经营选择和执行约束提供判断 |
| 02 财务分析 | 先从数字反推公司，再检验管理层叙事；形成可证伪判断 | 提供财务基线、异常和待验证问题 |
| 03 商业模式 | 解释需求、经济引擎、竞争与延续现有轨迹的结果 | 给 04 提供战略之外的基线，给 06 提供经营机制 |
| 04 战略决策 | 识别真实战略、资源投入、反事实、情景和证伪条件 | H2/H3/H5 等交接影响 06，H4 等影响 07 |
| 05 股性分析 | 解释历史价格表现、驱动因素和定价框架 | 帮助 07 选估值主锚，并辅助技术分析 |
| 06 财务预测 | 将上游判断转成三情景假设及分歧驱动表 | 驱动表是 07 情景计分和后续跟踪的中心接口 |
| 07 估值分析 | 判定主导情景、选择主锚、输出机会类型及切换条件 | 注册表、扫描、持仓建议、研究总结消费其结果 |

因此，02 并不等于“事实层”，03 也不是孤立的公司介绍。整篇报告通常同时包含证据、推断与假设，不能靠移动文件名完成事实与判断分离。

当前主流程的文化模块也不能简单等同于备份中的独立 `corporate-culture-analysis`：前者仍由三个子 skill 合成，后者是另一套独立分析方法。备份中存在某个 skill，不代表编排已经调用它。

### 2.2 已有两个不同的研究反馈入口

**事件更新：** 新事件 → 比对 06 驱动、04 领先/证伪条件、注册表切换信号 → 判断 L0–L3 影响和最小刷新集 → 审批后定向刷新。财报例行更新至少进入 L1；结构性事件可能上溯商业模式、战略或文化。每日扫描可以建议刷新，但不自动调用这套流程。

**预测偏差分诊：** 新一期实际值 → 对照既有假设和驱动表 → 核对连续越界、跨两档、关键指标同向偏离等触发条件 → 一级参数反馈，或二级上游重审。二级的检查顺序是商业模式 → 战略 → 企业文化，找到足以解释偏差的层级后停止继续上溯。

两者在 skill 中明确并存、互不调用。偏差分诊写 `_deviation` 判定单，但不改正式档案、注册表，也不派发刷新。故“只读不写”应理解为不修改生产研究状态，不能理解为没有研究记录产出。

### 2.3 已有版本与决策纪律

正式档案更新遵循：准备上下文 → `_pending` 产出 → finalize/交接检查 → accept/reject → `_history` 留存旧版 → 注册表同步。历史目录负责保存旧状态；交接块负责压缩当前有效结论，不应被改造成不断累加的日志。

每日持仓顾问另外检查“原来怎么说、现在怎么做”，包括事件条件过期、旧触发器与新估值不一致、买入后再改估值等情况。模拟组合已有独立持仓、成交和净值记录。它们都是反馈的一部分，但评价对象分别是执行纪律和组合规则，不能直接代替公司认识是否正确的检验。

短期交易也已有基础：技术分析提供时点、条件、止损和失效边界，股性分析解释价格表达方式。扫描器使用确定性脚本生成技术信号，不等于每天完整执行一次 `technical-analysis` skill。

### 2.4 现有估值有明确的方法约束

主流程采用“主导情景 × 单一主锚”，明确禁止概率加权目标价和多方法加权目标价。战略正文允许某些概率加权参考，但禁止传入正式价值锚。独立 VC 估值则有自己的概率和回报计算，不能把它的规则混进主流程。

因此，此前概率预测、校准评分等建议如需保留，应作为独立评价工具论证，不能直接替换现有估值决策规则。这里是在描述用户系统的选择，并非声称该方法已经被证明优于其他估值方法。

## 3. 规则与本地运行证据的区别

| 核对项 | 本地证据 | 能得出的结论与边界 |
|---|---|---|
| 偏差分诊是否真正用过 | `LLY 礼来/研究档案/_deviation/2026-08-22_FY26Q2.md`，有实际值、缺失项、触发核对及建议 | 至少有一个实际实例；不能据此证明已常态覆盖全库 |
| TCOM 是否已有相同分诊 | 当前 TCOM 无 `_deviation`；在当前 companies 树下找到的该目录仅 LLY 一处 | 本地未见 TCOM 分诊记录；不能推断 Cowork 其他位置或历史会话中从未做过 |
| TCOM 是否适配该分诊 | skill 明确排除本币申报的外币 ADR；TCOM 财务报告采用 RMB | 按现有规则不能直接照搬，需要先解决数据口径和适用范围 |
| TCOM 是否留存正式审批状态 | `_meta.json` 将 02/06/07 标为 2026-09-17 approved，并存在历史快照 | 有版本发布记录；不必仅凭事件评估文档仍写“待批准”就认定未发布 |
| TCOM 上游版本是否清楚 | 02 正文写 `source_period=2026Q2`；06/07 仍有 02 为 Q1/旧格式的描述；meta 的 source_period 为 null | 存在来源期与引用描述不一致；尚不能仅凭这点证明模型没有用 Q2 数据 |
| 是否具有战略模块 | 当前 TCOM 无 04；06/07 明示未提供 | 现有老档案允许 OPTIONAL_MISSING，不能把合规缺省直接判成系统失效 |
| 事前与事后证据是否已有意识 | TCOM 07 对新增交通票务阈值注明“读数已知后设定，弱证据” | 已经识别回看偏差；演化层应保存这类区分，不能重新包装成事前命中 |

LLY 实例还说明了反馈覆盖度的实际限制：六行驱动只有两行可计分，其余依赖产品、价格、份额或事件资料。缺失不等于验证通过。之后的演化视图应同时显示“判断结果”和“有多少关键问题本期根本无法验证”。本报告不重新核实该报告的投资事实，也不认可其所有推断。

## 4. 先解决接口问题，再考虑大搬目录

以下是可复查的文本或代码差异，不等于已经确认生产事故。

1. **扫描器仍使用旧同步接口。** daily-portfolio-scanner 第 0a 步读取 `slot06_path` 并抽取“加权目标价”；实际 `dossier_orchestrator.py` 入队字段为 `slot07_path`，`sync_valuations.py` 的 drain 也读取后者，并含加权目标价禁用检查。需要统一 skill 与脚本的调用契约，不能让扫描器另做一套人工解析。
2. **主导情景切换的写入权限冲突。** valuation-analysis 1.3/4.2 允许重新计分后只改 registry；research-event-update 则要求重跑 07 并走审核。需要明确哪条为准，尤其是“价格锚没变、情景判定变了”属于哪种发布动作。本次不擅自替用户选择。
3. **事件刷新同批依赖的描述不清。** event skill 同时要求 06→07 串行，又要求上游只读当前权威版、不读 pending。TCOM 07 实际注明使用同批 pending 的 06 v4.1；全量建档也有同批依赖消费规则。应明确“本批受影响模块用本批成品，未刷新模块用已批准版”的适用边界，并由批次清单记录实际使用版本；这是待确认的修订建议。
4. **战略 skill 的引用文件未随本次备份出现。** 它要求的 `references/research-protocol.md`、`decision-framework.md`、`output-template.md` 在备份目录内不存在。只能确认这份导出不完整，不能据此认定 Cowork 原环境缺失。

在这些接口统一前搬目录，会让路径变化与规则变化同时发生，增加追查困难。

## 5. 三个文件夹应该承载什么

用户提出的三层方向仍然适合，但它们是知识的组织方式，不应取代现有分析模块。

| 层 | 内容 | 与现机制的关系 |
|---|---|---|
| 事实信息 | 原始披露、电话会、数据底稿、带出处的事实条目、口径与更正记录 | 承接 Wiki/raw 与财务底稿；区分“管理层说了什么”和“实际发生了什么” |
| 研究判断 | 当前有效的文化、财务推断、商业模式、战略、预测、估值，以及独立的交易计划 | 保留 01–07 的职责和交接；技术判断注明自己的期限与失效条件 |
| 判断演化 | 旧版快照、事件评估、偏差分诊、修改理由、审核发布关系、结果检验和方法修订 | 连接 `_history`、`_events`、`_deviation`；Wiki 提供人读入口 |

**不要把所有规范化数字都默认当作事实。** 财务底稿中的披露值、重算值、正常化值、预测值要区分。正常化利润等即使是精确数字，也包含分析选择。

**不要制造两份当前判断。** Wiki 可以呈现和链接现行结论，但不能同时维护一份可能不同于 07/registry 的目标价。事实层可存来源和观测，当前判断层保留权威解释，演化层记录解释如何变化。

**运行状态应另外处理。** `_pending`、队列、缓存、运行日志是工作流设施，不应为了凑齐三类而伪装成研究知识。全局 `_system` 继续承担编排和跨公司注册；未批准产出继续有明确隔离。

## 6. 真正需要增强的，是一次变化能否首尾连通

不必先为每句话新建数据库。先选 06 分歧驱动表和 04 证伪条件中的关键项，给它们稳定的标识。每次事件更新或偏差分诊形成一张变化记录，至少能回答：

1. **原来判断什么：** 链接事前版本、适用期、阈值和当时证据；标明是否事后补录。
2. **现在知道什么：** 新证据、披露时间、口径、可比性和缺失项。
3. **改变哪一层：** 只改参数，还是推翻经营机制、战略或执行能力判断；也允许维持原判断并解释理由。
4. **改了什么：** 链接旧版、新版、批准批次、模型参数和主导情景变化；待批准与正式生效分开。
5. **投资与交易怎样受影响：** 长期价值判断和短期执行计划分别记录，不能用一方的理由事后挽救另一方。
6. **以后如何验证：** 下一次检验条件、到期结果、仍未解决的问题，以及是否需要修改分析方法。

这张记录连接现有产物，而不是取代事件评估、分诊报告或全量档案。Wiki 的价值在于让人从一条判断一路走到当时证据、后来检验、修改理由和决策结果。

评价也应分开：公司理解是否经得住新证据，预测误差是否改善，交易是否按事前规则执行，组合结果是否扣除成本后具有可解释性。单次赚钱不能证明判断正确；单次判断正确也不能证明整个系统已持续改善。

## 7. 下一步的最小验证范围

先以 TCOM 的 2026-07 与 2026-09 两次更新为样本，重建“旧判断—新证据—评估—06/07 新版—发布—后续待验”的链接。已知后设置的阈值只用于解释历史，不计为成功预测。对人民币、ADS、GAAP/调整口径、单季/TTM/全年和监管事件前后分别标明可比性。

同时用已有 LLY 分诊作为第二个样本，检查变化记录能否容纳“数据不足所以未能检验”。先验证这套表达能忠实容纳现有机制，再制定路径映射、脚本兼容和迁移验收。当前不应按旧草稿直接搬迁公司文件夹。
